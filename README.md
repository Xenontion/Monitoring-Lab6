# Monitoring-Lab6
# Моніторинг контейнерів та інфраструктури в Portainer і Eureka

Проєкт лабораторної роботи, присвячений комплексному моніторингу контейнеризованих сервісів у середовищі Docker. Рішення демонструє поєднання інфраструктурного моніторингу на рівні вузлів і контейнерів за допомогою **Portainer CE** та моніторингу логічної доступності компонентів на рівні сервіс-дискавері через **Eureka Server** (Spring Cloud Registry).

---

## 📌 Архітектура системи

Система складається з чотирьох взаємодіючих контейнерів, розгорнутих у спільній bridge-мережі `lab6-net`:

1. **`portainer`** (порти `9000`, `9443`) — вебінтерфейс для адміністрування Docker-ноди, контролю життєвого циклу контейнерів, збору логів і спостереження за метриками CPU, RAM, Network I/O.


2. **`eureka-server`** (порт `8761`) — сервер реєстрації мікросервісів з вебінтерфейсом (Spring Cloud / Eureka Discovery Dashboard). Приймає реєстраційні запити та періодичні heartbeat-пакети. Якщо сервіс не оновлює статус понад 15 секунд, він позначається як `DOWN`.


3. **`order-service`** (порт `8081`) — стабільний мікросервіс на базі FastAPI. Автоматично реєструється в Eureka, кожні 5 секунд надсилає сигнали життєздатності (`UP`) та надає ендпоінт для генерації навантаження на процесор. Має обмеження ресурсів: `cpus: '0.5'`, `memory: 256M`.


4. **`unstable-service`** (порт `8085`) — проблемний мікросервіс на базі FastAPI, розроблений для симуляції збоїв. Після короткої реєстрації в Eureka сервіс аварійно перериває процес через імітацію критичної помилки пам'яті (`OutOfMemoryError`), переходячи у стан циклічного перезапуску Docker-демоном (`CrashLoopBackOff` за політикою `restart: on-failure:5`).

## 🚀 Швидкий запуск

### 1. Попередні вимоги

* Встановлений **Docker Desktop** (або Docker Engine з плагіном Docker Compose)
* **Python 3.10+** (для виконання скрипту `trigger_load.py`)

### 2. Запуск контейнерів

У кореневій директорії проєкту виконайте команду збирання образів та фонового підняття сервісів:

```bash
docker compose up --build -d

```

Перевірте коректність запуску всіх чотирьох контейнерів:

```bash
docker compose ps

```

Усі сервіси (`portainer`, `eureka-server`, `order-service`, `unstable-service`) повинні бути ініціалізовані.

## 🖥️ Робота з інтерфейсами та моніторинг

### 1. Вебінтерфейс Portainer

* **URL:** [http://localhost:9000](http://localhost:9000)
* **Перший вхід:**
1. За необхідності отримайте токен налаштування за допомогою команди:
```bash
docker logs portainer

```


2. Задайте пароль адміністратора (не менше 12 символів) та натисніть кнопку створення облікового запису.
3. Оберіть локальне Docker-середовище (**`local`**).


* **Моніторинг:**
* У розділі **Containers** доступний загальний список контейнерів, їх статуси (`running`, `restarting`), відкриті порти та внутрішні IP-адреси.


* Натискання іконки **Stats** навпроти контейнера відкриває графіки використання пам'яті (Memory usage), процесора (CPU usage) та мережевого трафіку в реальному часі.


* Натискання іконки **Logs** дозволяє переглядати журнал стандартного виводу із підтримкою часових міток (**Display timestamps**).





### 2. Вебінтерфейс Eureka Dashboard

* **URL:** [http://localhost:8761](http://localhost:8761)
* Відображає таблицю зареєстрованих мікросервісів:
* `ORDER-SERVICE` підтримує активний статус **`UP`** завдяки регулярним фоновим heartbeat-запитам.


* `UNSTABLE-WORKER` після аварійного завершення припиняє надсилання оновлень і динамічно переходить у статус **`DOWN`**.

## ⚡ Генерація навантаження та перевірка аномалій

1. **Тестування навантаження на процесор:**
Запустіть клієнтський скрипт:
```bash
python trigger_load.py

```


Скрипт надсилає пакет запитів на розрахунковий ендпоінт `order-service`. У вкладці **Stats** контейнера `order-service` у Portainer спостерігається фіксація полиці навантаження до ~50% (повне вичерпання виділеного ліміту `cpus: '0.5'`) та наступний спад до 0% після завершення тесту.


2. **Діагностика збою застосунку:**
У розділі **Containers** Portainer знайдіть контейнер `unstable-service`. Відкрийте його логи (**Logs**) та активуйте тумблер **Display timestamps**. Записи демонструють регулярні перезапуски сервісу з інтервалом ~19 секунд через завершення процесу, що ілюструє різницю між фізичною наявністю контейнера в системі та логічною недоступністю сервісу в реєстрі Eureka.
